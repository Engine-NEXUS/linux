## C2-1 — Eagerness (status)

* **Mechanism (OpenAI Realtime VAD guide, P):** two modes. `server_vad` = silence-based (`threshold`, `prefix_padding_ms`,
  `silence_duration_ms`). `semantic_vad` = a classifier on the *words* estimates whether the user is done; it **scales the maximum wait
  timeout by that confidence**; `eagerness` low / medium / high (auto = medium) shifts the timeouts. The guide gives no numeric timeouts.
* **Ours:** `turn_detect::{Eagerness, policy_for}` already maps this onto Smart Turn (min-silence / threshold / patient limit).
* **Refinement (only if the eval supports it):** make the wait a *continuous* function of the model probability
  (`limit = lerp(patient, base, p)`) instead of the current two-level hold-open. Our numbers (240/400/560 ms etc.) are **our own
  hypotheses**, not OpenAI's.

## C2-2 — Directed-speech & false-trigger mitigation  → **Phase 8 — IMPLEMENTED 2026-10-05 (change 82); live evaluation pending**

### How Apple does it (P: Apple ML Research "Voice Trigger System for Siri"; S: arXiv 2001.10822)

1. **Stage 1 — always-on streaming detector** (DNN-HMM, 23 output states, 4-bit weights): tuned for **recall**.
2. **Stage 2 — high-precision checker** (Conformer encoder + CTC): re-scores candidates; discriminative training against
   phonetically similar phrases ("seriously", "cereal").
3. **Stage 3 — speaker ID** (LSTM embeddings vs. enrolled profile).
4. **Stage 4 — false-trigger mitigation (FTM)**, three independent subsystems:
   * *lattice-based* — true triggers have **few competing ASR hypotheses**; false ones show many alternative paths/unexpected words
     (GNN over the lattice: ~87 % of false triggers removed at 99 % true-positive rate, per the paper);
   * *acoustic-based* — streaming transformer on audio features only (prosody, SNR);
   * *text-based* — BERT-like model for **non-vocative uses and non-device-directed speech**.
   Compute grows stage by stage and later stages run only when earlier ones pass.

### What NEXUS has today (code)

| Apple stage | NEXUS equivalent | State |
|---|---|---|
| 1 recall detector | openWakeWord `nexus.onnx` (recall 97.5 %, FA 1.67 %) | ✅ |
| 2 precision checker | STT cross-check `verify_candidate` (`verify_transcript_gated`, no_speech veto); `read_verify_wake` | ✅ (default per settings; code default `false`) |
| 3 speaker ID | `verify_speaker_at_fire` (`speakerVerification`, default off) | ◐ |
| 4a lattice uncertainty | Whisper-verbose **segment stats** exist (`no_speech`, avg log-prob) but only the no_speech veto is used | ◐ |
| 4b acoustic FTM | – | ❌ |
| 4c text-based directed-speech | **none**. In ghost hot-mic loops an unrecognised utterance becomes `ParsedIntent::Unknown → Subsystem::WorkerBackend` (cloud chat) — `orchestrator.rs:582` — so TV/room speech can reach the LLM | ❌ **the gap** |
| – | TTS echo rejection by *content*: only RMS/time gates; barge-in relies on "exact phrase" rule | ◐ |

### Mechanism worth borrowing from isair's docs (R, ideas only)

An **"intent judge"** runs on a speech segment *only if an engagement signal exists* (wake word seen, hot window active, or TTS
playing); ambient speech with no engagement skips it. Inputs: rolling transcript (~120 s), wake timestamp, **last TTS text + finish time
(echo rejection)**, state flags. Output: `{directed, query, stop, confidence}`. It falls back to text-based wake detection if the judge
model is unavailable. Also: a **"recall gate"** (deterministic, no LLM) that skips memory lookups when the hot window already grounds the
follow-up (≥ 50 % content-word overlap + a fresh tool result), and **KV-cache discipline** (byte-static system prompts, per-call data at the tail).

### Design for NEXUS — `directed.rs` (new, pure + testable)

**Where it applies:** only for turns that did **not** start from an explicit wake/hotkey — i.e. ghost **hot-mic relisten turns** and
(optionally) post-TTS follow-ups. A turn the user *just woke* is always accepted (they addressed us).

**Score, deterministic first (no model, < 1 ms):** features →
1. `parses_as_command` — the existing intent parser returns a non-Unknown intent ⇒ accept (strongest signal; the grammar is already conservative).
2. `has_vocative` — contains "nexus" / known mishearing aliases (reuse `normalize_phonetic_mishearings`).
3. `echo_overlap` — token overlap with the **last N seconds of our own TTS text** (we know exactly what we said) ⇒ reject if ≥ 0.6 (fuzzy, order-insensitive).
4. `stt_confidence` — Whisper-verbose `no_speech_prob` / `avg_logprob` / `compression_ratio` of the segments (the lattice-uncertainty analog).
5. `shape` — length, question/imperative cues, second-person pronouns, filler/no-verb fragments.
**Decision:** accept if (1) or (2); reject if (3) or STT confidence is poor; otherwise **ambiguous** → `Ignore` (silent, logged) in hot-mic mode.
**Optional layer (only if measured need):** a tiny logistic regression over the same features, trained on our own logs
(`missed_intents.jsonl`, diary) — no LLM in the hot path. An LLM judge (the isair approach) costs cloud latency + tokens; keep it
as a fallback for the ambiguous band *only if* the deterministic layer's false-ignore rate is too high.

**Integration points:** `orchestrator.rs` just before the `Unknown → WorkerBackend` fallthrough, gated by "turn origin = hot-mic";
a `turn_origin` flag passed from the relisten path (`ghost.rs` relisten / frontend `maybeGhostRelisten`). Never applied to the first turn after wake.

**Privacy:** ignored utterances are logged as text only, locally, rotated (same policy as `missed_intents.jsonl`); nothing leaves the device.

### Acceptance tests (must be written *before* enabling)
1. Table tests per feature (pure functions).
2. Labelled set: ≥ 100 directed commands (from `missed_intents.jsonl` + e2e fixture) and ≥ 100 non-directed lines
   (TV/podcast snippets, side conversation, our own TTS replies). Targets: **false-accept ≤ 2 %**, **false-ignore ≤ 5 %** on directed commands. Numbers are goals, not facts.
3. Echo test: replay each NEXUS spoken line as transcript ⇒ 100 % rejected.
4. Soak: 8 h of mixed audio with ghost hot-mic on ⇒ zero LLM calls from non-directed speech.
5. Regression: the full command fixture (49/50) unchanged.

### Risks
* False-ignore of a legitimate but unusual command in hot-mic mode → mitigate with a brief earcon/orb flick on "heard but ignored" and a one-shot "did you mean me?" only after repeated ignores (anti-nag, same pattern as the existing silent-miss cap).
* Echo overlap vs. a user who repeats NEXUS's words ("open whatsapp" after we said "Opening WhatsApp") — require overlap on **our sentence**, not on the command keyword; test it.

## C2-4 — Screen-context memory (Screenpipe-style)  → **Phase 10, design only**

**Mechanism (P: docs.screenpipe.com/architecture):** event-driven capture on app switch, window focus, click/scroll, typing pause,
clipboard copy, plus an idle fallback (~5 s); **accessibility-tree text first, OCR fallback** when the tree is empty (remote desktop, games);
frame de-duplication; SQLite with `frames`, `elements` (FTS5), `audio_*`, `ui_events`; claimed ~600 MB RAM, 5–10 % CPU, 5–10 GB/month
(vendor figures, not verified). Privacy filter strips PII before any AI sees data; retention policy configurable.

**NEXUS already owns the hard parts:** UIA walker (Ghost Mode), `ocr.rs` (Windows OCR), `pii_filter.rs`, `diary.rs`, meeting/privacy detection
(`meeting_detect.rs`), app denylist (`live/safety.rs`).

**Proposed minimal design (not for implementation until you approve scope):**
* **Opt-in, default off**, visible indicator while on, one-key pause.
* Capture **text only** (UIA first, OCR fallback), no screenshots stored; trigger = foreground-window change + typing-pause debounce (skip idle polling).
* Hard denylist: password managers, banking, anything in `safety.rs` denylist, private/incognito browser windows, UIA password fields; auto-pause during meetings.
* PII redaction **before** writing; SQLite FTS5 table in the Phase-4 memory DB; retention default 7 days, user-configurable; "forget the last N minutes" voice command.
* Query path: "what was that error I saw earlier?" → FTS5 search → LLM answer with citations (window title + time).
* Success criteria: recall@5 on a seeded 50-question set; CPU < 3 % average on this laptop; DB growth measured per day; zero captures from denylisted apps in a scripted test.

**Why design-only now:** it records everything on screen. Scope, retention and consent are *your* decisions — see questions at the end.

## C2-5 — Proactive speech timing  → **Phase 9 — IMPLEMENTED 2026-10-05 (change 83); live evaluation pending**

### What the research says (P: arXiv 2106.02077, CUI 2021)
People interrupt **sooner when it is urgent**; they time interruptions around **breakpoints** in the other person's task; they vary phrasing/delivery
by urgency; a minority use an **access ritual** (a heads-up like "excuse me…") first. The abstract gives **no numbers** — every threshold below is our hypothesis to tune.

### What NEXUS does today
`google/sentinel.rs` decides only by urgency (`should_speak_immediately(urgency, min_threshold)`), then `orchestrator::speak_proactive_alert` →
`speak_line` immediately. It does **not** check whether the user is speaking, in a call, mid-command, mid-Ghost-drill, or has TTS playing.

### Design — `proactive_policy.rs` (pure state machine + tests)
Inputs (all already tracked): `stt_capturing`, `tts_playing`, `ghost::drill_running()`, `meeting_active`/paused, user-voice-activity recency,
foreground-fullscreen flag, time since last user interaction, alert urgency, alerts spoken in the last hour.
Output: `Speak(style) | Defer(until breakpoint) | CardOnly | Drop`.
* **Critical:** speak within ≤ 2 s unless in a meeting/call (then orb pulse + card, speak at the first breakpoint).
* **High:** wait for the next *breakpoint* (turn just ended, drill finished, user idle ≥ ~5 s) with a ~60 s ceiling.
* **Medium:** only when the user has been idle ≥ ~30 s, else queue as a sidebar card.
* **Low:** card only, never voice.
* **Access ritual:** a 300 ms earcon/orb nudge, then speech; speech opens with a short urgency-scaled lead-in. User can say "not now" → snooze 15 min.
* **Rate limits:** cooldown between spoken alerts, max N per hour, never repeat the same alert id.
* Phrasing varies by urgency (short imperative for Critical; polite summary for Medium).
**Acceptance:** table tests over (state × urgency); simulated-timeline tests (alert arrives mid-meeting → deferred → spoken at the first breakpoint exactly once);
no regression in the existing sentinel tests (34 google tests). **Live:** a week of use with a "was this alert badly timed?" thumbs flag stored locally.

## C2-6 — Moshi / C2-7 VAP / C2-8 Unmute — defer

* **Moshi (arXiv 2410.00037, S):** full-duplex speech-text model, ~160 ms theoretical / ~200 ms practical latency; GPU-class; paper licence CC BY-NC-SA 4.0; code/weights licence **not verified here**. Not laptop-friendly. Watch only.

Interesting twist for us: we *know* our own TTS signal, so a (mic, TTS) stereo input is constructible — worth revisiting only if the Smart Turn eval shows turn-taking remains the top pain.
* **Unmute (S):** GPU stack, no licence stated. Skip.
